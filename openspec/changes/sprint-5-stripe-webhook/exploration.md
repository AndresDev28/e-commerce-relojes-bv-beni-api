# Sprint 5 — Gap #1: Stripe webhooks for payment intents

## Context

The backend currently processes only `charge.refunded`, while the frontend still marks an order as `paid` during the client-side order creation flow. Frontend PR #127 now creates the canonical `orderId` server-side and sends `metadata.orderId` and `metadata.userId` when creating the PaymentIntent, creating the correlation contract required for server-side reconciliation. This cycle investigates `payment_intent.succeeded` and `payment_intent.payment_failed`, including the race where Stripe delivers the webhook before `useCreateOrder` creates the Strapi Order.

## Current State

### Webhook entry point and handler

- `POST /api/orders/stripe-webhook` is an unauthenticated custom route (`src/api/order/routes/01-custom.ts:7-12`). The controller reads the `stripe-signature` header and prefers `ctx.request.body[Symbol.for('unparsedBody')]` over the parsed body, then delegates to `strapi.service('api::order.stripe-webhook').handleStripeWebhook(...)` (`src/api/order/controllers/order.ts:323-337`). Signature/configuration errors are returned as HTTP 400; other errors are returned as HTTP 500 (`src/api/order/controllers/order.ts:338-350`).
- `handleStripeWebhook(signature, unparsedBody)` first requires `STRIPE_WEBHOOK_SECRET` and `STRIPE_SECRET_KEY`, constructs a Stripe client with the pinned `2026-01-28.clover` API version, rejects a missing raw body, and calls `stripe.webhooks.constructEvent(unparsedBody, signature, endpointSecret)` (`src/api/order/services/stripe-webhook.ts:13-46`). Signature failures are logged and replaced with the generic error `Webhook signature verification failed.`
- After logging the event type, the handler has one event branch: `charge.refunded` (`src/api/order/services/stripe-webhook.ts:48-85`). It extracts the PaymentIntent ID from either a string or expanded object, acknowledges the event when that ID is absent, queries Orders with legacy `strapi.entityService.findMany` filtered by `paymentIntentId`, acknowledges when no order is found, selects the first result, and acknowledges without updating when the order is already `refunded` (`src/api/order/services/stripe-webhook.ts:49-72`). Otherwise it uses legacy `strapi.entityService.update` to set `orderStatus: 'refunded'` and `statusChangeNote` (`src/api/order/services/stripe-webhook.ts:74-79`).
- Unhandled event types are logged and still acknowledged with `{ received: true }` (`src/api/order/services/stripe-webhook.ts:86-90`). The existing event dispatch therefore has a clear sibling-event seam, but the refund branch currently mixes event dispatch, lookup, idempotency, and mutation in one method. Any new branches must preserve its current lookup, terminal-state guard, error behavior, and lifecycle side effects.
- The handler uses legacy Entity Service CRUD. The lifecycle code already demonstrates the repository's mixed convention: Entity Service for numeric-ID reads/updates and Document Service where Strapi v5 `documentId` behavior matters (`src/api/order/content-types/order/lifecycles.ts:207-224`, `:346-363`). The init convention records Document Service as preferred for `findOne` (`Engram #320`), so the API choice is an implementation concern for proposal/design, not a behavior currently provided by this handler.

### Order lifecycle behavior relevant to reconciliation

- `beforeCreate` assigns the authenticated request user with Strapi v5 `connect` syntax, preserves a programmatic `data.user`, and validates each item against current stock (`src/api/order/content-types/order/lifecycles.ts:105-151`). A webhook request has no normal authenticated user context, so a webhook-created Order would need an explicit user relation in its input or would enter the no-user warning path.
- `afterCreate` always attempts an initial status-history entry (`src/api/order/content-types/order/lifecycles.ts:158-172`). It then decrements every item stock when `orderStatus !== 'cancelled'` and `items` is an array (`src/api/order/content-types/order/lifecycles.ts:174-185`). For that same non-cancelled/items path it sends the initial email webhook with `isNewOrder: true` (`src/api/order/content-types/order/lifecycles.ts:186-188`). Thus the current hook decrements stock for `pending` as well as `paid`; it is not payment-authority-aware.
- `beforeUpdate` loads the current status through Document Service when `where.documentId` is present and Entity Service when `where.id` is present, validates changed statuses with `validateOrderTransition`, and stores the previous status and optional `statusChangeNote` in `event.state` (`src/api/order/content-types/order/lifecycles.ts:202-264`).
- `afterUpdate` skips history and email when the status is unchanged (`src/api/order/content-types/order/lifecycles.ts:272-287`). On a real change it creates a history entry, restores stock when entering `cancelled` or `refunded` from a non-refund state, may create a Shipment for `shipped`, sends the email webhook with `isNewOrder: false`, and triggers the frontend refund flow when the new status is `refunded` (`src/api/order/content-types/order/lifecycles.ts:298-422`). The stock restoration helper call is `updateProductStock(item.id, item.quantity)` (`:307-323`).
- `sendOrderEmailWebhook` is disabled only when `DISABLE_EMAIL_NOTIFICATIONS === 'true'`; otherwise it re-reads the Order with populated `user` and `shipment`, requires a user email, and calls `${FRONTEND_URL}/api/send-order-email` (`src/api/order/content-types/order/lifecycles.ts:16-101`). A webhook-created Order through Entity Service would therefore use the normal lifecycle email path if its user relation and items are valid.

## Findings

- **1. Handler shape and compatibility.** The current contract is signature verification first, event-type dispatch second, payment-intent correlation third, then a status mutation through Entity Service. `charge.refunded` has no event-record table or event-ID persistence; its idempotency is only the `orderStatus === 'refunded'` guard (`src/api/order/services/stripe-webhook.ts:69-79`). The existing branch must remain reachable and retain its current acknowledgement behavior for missing PaymentIntent IDs and missing Orders (`:52-65`). `payment_intent.succeeded` and `payment_intent.payment_failed` can be investigated as additional event types over the same verified `Stripe.Event`; they will need separate status/data rules because their payload object is a `Stripe.PaymentIntent`, not a `Stripe.Charge`.

- **2. Stock and ordering race.**
  - **Webhook before `useCreateOrder`:** the current handler finds no Order by `paymentIntentId` and returns 200, so no Order, status change, history, stock change, or email is produced. The payment can consequently remain successful in Stripe without a backend Order.
  - **Webhook after an existing Order:** the frontend currently creates the Order with `orderStatus: 'paid'`; `afterCreate` has already decremented stock. A later succeeded webhook must be understood as reconciliation of an already-paid Order, not as a second stock reservation. If the existing Order was created as `pending`, its current `afterCreate` hook has still already decremented stock, and a status-only transition to `paid` does not itself decrement stock.
  - **Client creation never occurs:** current behavior leaves the successful PaymentIntent orphaned. The webhook metadata contains `orderId`, `userId`, `itemsCount`, `subtotal`, and `shipping` (frontend `createPaymentIntentService.ts:118-155`), but not the required item lines. The Order schema requires `orderId`, `items`, `subtotal`, and `total` (`src/api/order/content-types/order/schema.json:14-33`); `total` can be inferred from the PaymentIntent amount, but the item JSON cannot be reconstructed from the current metadata contract. This makes “create the complete Order from the webhook alone” a contract question, not an already-supported path.
  - Creating an Order through the normal Entity Service path would invoke `beforeCreate` and `afterCreate`, including stock decrement, history, and the initial email path. Directly decrementing stock in the webhook and later allowing the frontend Order creation path would expose a double-decrement risk. Conversely, bypassing lifecycle creation would require separately accounting for the missing history, user relation, stock, and email effects. The repository has no explicit stock-reservation marker to distinguish “stock already decremented” from “not yet decremented.”
  - `updateProductStock` reads current stock and then writes the new value (`src/api/order/services/order.ts:48-73`); there is no visible transaction, row lock, or compare-and-set. Concurrent webhook deliveries therefore require more than a status check to establish atomic stock behavior.

- **3. Status state machine.** `OrderStatus` contains `pending`, `paid`, `processing`, `shipped`, `delivered`, `cancelled`, `refunded`, and `cancellation_requested`; it has no `payment_failed` value (`src/core/domain/order/order.types.ts:13-21`, `src/api/order/content-types/order/schema.json:35-48`). `pending → paid` is valid, `paid → processing` is valid, and `cancelled`/`refunded` are terminal (`src/core/domain/order/order.types.ts:62-71`). The three failure-status choices have materially different effects:
  - Marking the Order `cancelled` uses an existing terminal state and causes `afterUpdate` to restore stock when entering it (`lifecycles.ts:307-323`), but it conflates a payment failure with cancellation and emits the existing cancellation notification semantics.
  - Adding `payment_failed` would require changing the Order schema enumeration, the domain type and transition matrix, status-history enumerations (`src/api/order-status-history/content-types/order-status-history/schema.json:14-39`), generated types, and the frontend status/email contracts. Its stock and retry transitions would also need explicit definition.
  - Keeping the Order `pending` and recording failure data in `paymentInfo` requires no new Order status value and can use the existing JSON field (`src/api/order/content-types/order/schema.json:59-61`), but it does not create an `afterUpdate` status transition/history/email event and leaves the current `afterCreate` stock decrement semantics unchanged. It also cannot record anything when no Order exists.
  No choice is made here.

- **4. Idempotency and Stripe delivery.** Stripe documents automatic live-mode retries for up to three days with exponential backoff, and sandbox retries three times over several hours ([Stripe webhook event deliveries](https://docs.stripe.com/webhooks)). The current handler returns 200 for an unhandled event, absent PaymentIntent ID, or absent Order, so Stripe will not retry those cases; it throws for processing failures, which the controller maps to an error response. There is no persisted Stripe event ID or processing ledger. `paymentIntentId` is not marked unique in the Order schema (`schema.json:50-52`), and the refund branch uses `findMany` then takes `orders[0]` (`stripe-webhook.ts:58-67`).
  - A duplicate succeeded event for an existing `paid` Order can be recognized by the existing status and should not cause another stock change; `afterUpdate` also skips work when the status is unchanged (`lifecycles.ts:284-287`). A duplicate succeeded event after a webhook-created Order would still need to correlate by `paymentIntentId` before considering `metadata.orderId`, because the second delivery has the same PaymentIntent identity.
  - A late succeeded event for `processing`, `shipped`, `delivered`, `cancelled`, or `refunded` is not equivalent to the normal `pending → paid` transition. The current state matrix rejects those changes or treats terminal states as immutable. The behavior for out-of-order events is not currently defined.
  - The `orderId` field is unique, but `paymentIntentId` is not. The codebase therefore has two possible correlation keys with different enforcement: a database-enforced Order ID and a non-unique PaymentIntent field. Concurrency between duplicate deliveries and frontend creation is not visibly serialized.

- **5. Frontend coupling and missing metadata.** PR #127's current frontend implementation generates `orderId` only after server-derived `userId` validation and before the Stripe API call (`e-commerce-relojes-bv-beni/src/features/checkout/services/createPaymentIntentService.ts:106-123`). It sends `metadata.orderId` and `metadata.userId`, plus `itemsCount`, `subtotal`, and `shipping` (`:141-155`). The frontend then passes the same `orderId` to `POST /api/orders`; `useCreateOrder` assembles the complete item/totals payload and sets `orderStatus: paid`, `paymentIntentId`, and `paymentInfo` (`e-commerce-relojes-bv-beni/src/features/checkout/hooks/useCreateOrder.ts:37-66`; `src/features/checkout/services/assembleOrderData.ts:41-59`).
  - The backend can rely on the PR #127 contract only for PaymentIntents created by that frontend version: `metadata.orderId` is the canonical Order identifier and `metadata.userId` is the server-derived canonical Strapi user identifier. It cannot assume those keys exist on legacy PaymentIntents or on other/misconfigured clients. The current backend fallback is a `paymentIntentId` lookup, which only works after an Order has been created.
  - If metadata is absent, the remaining safe correlation evidence is the PaymentIntent ID and the eventual client Order payload. Metadata absence therefore leaves the orphan-reconciliation behavior undefined; it is not equivalent to “the Order is missing.”

- **6. Test infrastructure and coverage needs.** `test/api/stripe-webhook.test.ts` resets the SQLite-backed Strapi state, sets `STRIPE_WEBHOOK_SECRET`, builds a valid header with `stripe.webhooks.generateTestHeaderString`, and posts raw JSON to `/api/orders/stripe-webhook` with `stripe-signature` (`test/api/stripe-webhook.test.ts:14-23`, `:44-68`). The existing five tests cover three refund flows and two configuration/signature error paths (`:25-182`). `createTestOrder` always requires a user and creates an Order through Entity Service (`test/helpers/strapi-test-helpers.ts:570-605`), so it is suitable for existing-order succeeded/failed cases but not for “no Order exists.”
  - The orphan case must start with a PaymentIntent payload containing metadata but deliberately omit `createTestOrder`; any expected created Order, relation, required item data, and stock effect depend on the unresolved reconciliation contract.
  - The investigation identifies test scenarios for: succeeded against an existing pending Order; succeeded against an already-paid Order with unchanged stock/history; duplicate succeeded delivery; succeeded before Order creation; legacy/missing metadata; failed delivery with `last_payment_error`/`failure_message`; out-of-order status; preservation of the existing refund path; valid and invalid signatures; and processing errors that should or should not be retried. Tests that exercise email side effects should explicitly account for `DISABLE_EMAIL_NOTIFICATIONS` (`lifecycles.ts:17-21`).

- **7. Failure payload, email, and adjacent stock implications.** Stripe's PaymentIntent webhook documentation shows `payment_intent.succeeded` as the server-side fulfillment signal and `payment_intent.payment_failed` as carrying failure details in `last_payment_error` ([PaymentIntent status verification](https://docs.stripe.com/payments/payment-intents/verifying-status)). The requested failure payload also exposes `failure_message`; the existing `paymentInfo` JSON field can hold audit data, but no backend shape or retention rule exists. A failure update to an existing Order would interact with `beforeUpdate`/`afterUpdate`; a failure with no Order has no current persistence target.
  - A normal Entity Service-created reconciled Order triggers `afterCreate`, including the initial email path (`isNewOrder: true`) when it is non-cancelled and has an items array. A subsequent status update triggers `afterUpdate`, status history, and a non-new-order email when the status changes. A direct stock mutation or direct database write would not automatically produce those lifecycle effects.
  - The existing email helper re-reads the user relation and silently skips delivery when no user email exists (`lifecycles.ts:24-33`). A webhook-created Order with a missing/invalid `userId` cannot be assumed to produce an email even when email notifications are enabled.
  - Stock is currently decremented at creation and restored on transition into `cancelled`/`refunded`; moving that responsibility to webhook processing would alter both lifecycle semantics and the behavior of client-created pending Orders. This is a refactor boundary for downstream design, not a decision made by this exploration.

## Open Questions

The following decisions are needed before proposal/design; items marked **BLOCKS PROPOSAL** prevent a complete proposal because the current event metadata cannot reconstruct a required Order.

1. **BLOCKS PROPOSAL — Orphan creation contract:** When `payment_intent.succeeded` arrives before `useCreateOrder`, should the backend create an Order, acknowledge and wait for the frontend, or use another reconciliation record? If it creates an Order, where do the required `items` and complete totals come from? Current metadata has no item lines.
2. **BLOCKS PROPOSAL — Stock authority:** Is stock reserved/decremented by the existing `afterCreate` lifecycle, by webhook processing for orphan payments, or by a redesigned single path? How is “already decremented” persisted across webhook-first and client-first races?
3. **BLOCKS PROPOSAL — Failure status:** Should failure mean `cancelled`, a new `payment_failed` state, or unchanged `pending` plus `paymentInfo`? The choice determines transition rules, history, frontend status contracts, and stock release behavior.
4. **BLOCKS PROPOSAL — Missing metadata:** What is the required behavior for legacy PaymentIntents without `metadata.orderId` or `metadata.userId`? Is PaymentIntent-ID-only lookup sufficient, and should unmatched events be acknowledged or retried?
5. **Idempotency boundary:** Is status-based idempotency sufficient, or must Stripe event IDs / PaymentIntent IDs be persisted with a uniqueness constraint? What should happen for duplicate or out-of-order events after an Order has advanced beyond `paid`?
6. **Failure audit contract:** Which fields from `last_payment_error` and `failure_message` may be stored in `paymentInfo`, and should sensitive Stripe error fields be excluded or redacted?
7. **Email semantics:** Should a webhook-created paid Order send the same initial purchase email as the client-created Order, and should a payment failure send an email when the selected failure behavior does not change `orderStatus`?
8. **API layer convention:** Should the new webhook logic remain on legacy Entity Service to match `charge.refunded`, or should the relevant lookup/mutation use Document Service in line with the Strapi v5 convention recorded in Engram #320?

## Adjacent Context

- **Gap #3 (frontend retry):** A retry around `useCreateOrder` would reduce the orphan window, but it is not part of this backend exploration. The webhook must still define behavior when the browser never retries.
- **Gap #4 (frontend idempotency key):** PaymentIntent creation idempotency is a separate frontend concern; it affects duplicate PaymentIntents, while this cycle must handle duplicate delivery for one PaymentIntent.
- **Gap #5 (stock timing):** The current `afterCreate` decrement is the direct side effect investigated here; its broader hardening remains adjacent and is not explored as a separate cycle.
- **Gap #6 (tax):** Tax calculation changes totals and therefore any future order-reconstruction contract, but it is out of scope.
- **Gap #7 (E2E):** Full browser-to-Stripe-to-Webhook coverage is future work; this cycle only identifies integration cases for the existing Vitest/Supertest infrastructure.
